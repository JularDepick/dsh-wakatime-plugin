# Tag&Release 规范

## 版本号

遵守 `v<主版本号>.<次版本号>.<修订版本号>` 格式,例如 `v0.1.0`.

> README的版本徽章显示文字中,版本号不带v字母前缀

## Tag

遵守 `<版本号>` 格式, 即带 `v` 前缀(例如 `v0.5.2`); 历史 tag 全部为该形态, README 的版本徽章链接也按此形态指向.

## Release

遵守 `<版本号>-dsh-<最高支持的dsh版本号>` 格式, 其中版本号**不带** `v` 前缀(与 Tag 不同), 例如 0.5.3 版本对应 `0.5.3-dsh-0.2.2-rc.5`.

> Release 名中的 dsh 版本取该产物支持范围内**已实测的最高版本**: 区间上界写作下一条次的第一个预发布(如 `<0.2.3-rc.1`)时, 名字里填区间内实测到的最高版本(当前 `0.2.2-rc.5`), 不要照抄区间描述.

> 同一份产物支持的是包清单声明的**实测区间**(`engines.dsh` 用区间字面写法, 七个宿主包的 peer 用等价的分段写法, 两者集合相同): 区间内的小版本 dsh 升级无需为每个 dsh 版本单独发布插件, 当前区间为 `>=0.2.1-rc.1 <0.2.3-rc.1`, 覆盖 0.2.2 整条预发布线与 0.2.2 正式版.

> 区间之外(下一条次的第一个预发布及之后, 含 0.3.x)一律拒绝安装与启动, 因此每当 dsh 进入下一条次时必须成对推进 `engines.dsh` 与 peer 的上界并发布新的 Release; 区间内同线的后续预发布由同一份产物直接放行, 但仍须先做发布包比对再宣布支持.
> 区间下界只在实测覆盖时下探, 不要为"看起来兼容"而放宽.
> 示例: 0.5.3 版本对应 Release 名 `0.5.3-dsh-0.2.2-rc.5`(区间 `>=0.2.1-rc.1 <0.2.3-rc.1` 内已实测的最高版本); 历史版本 0.5.2 对应 `0.5.2-dsh-0.2.2-rc.3`, 0.5.1 对应 `0.5.1-dsh-0.2.2-rc.2`, 0.4.1 的 Release 名为 `0.4.1-dsh-0.2.2-rc.1`, 0.3.0 的 Release 名为 `0.3.0-dsh-0.2.1-rc.3`, 各自当时区间上界分别为 rc.2, rc.1 与 rc.3.
